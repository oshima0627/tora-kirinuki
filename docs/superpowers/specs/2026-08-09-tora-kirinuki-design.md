# 令和の虎Second 切り抜きチャンネル — 設計

作成日: 2026-08-09

## 1. 背景

YouTube の切り抜きチャンネルを作る。当初はリベ大（両学長）を対象に検討したが、
[リベ大の著作物に関するガイドライン](https://site.libecity.com/copyright-guidelines) に
違反行為の例として「リベ大YouTubeなどの切り抜き動画を作成し、不特定多数が閲覧できる状態にする」
が明記されており、**リベ大は対象にできない**。許容されるのは出所明示を伴う引用のみ。

そこで切り抜きを公式に許諾しているクリエイターへ対象を変更した。
許諾のハブは [ガジェット通信クリエイターネットワーク](https://getnews.jp/mcn/kirinuki)で、
78クリエイターの申請フォームが公開されている。**ここに載っていない相手は原則NG**と考える。

### 選定結果: 令和の虎Second（`@reiwanotora_second`、登録者20.3万人）

理由:

- **MCN申請フォームがあり、手続きが確実**（令和の虎Youth は数値が良いがフォームが無く、個別確認が必要）
- **本編が健在**。直近の投稿は2日前・3日前・4日前・6日前…と隔日ペース、再生1.8万〜6.1万。素材供給が途切れない
  （比較: 青い令和の虎は直近120日の切り抜きが0本＝枠として停滞している）
- ビジネス系で、後述の図解による付加価値が最も効く題材

第三者の切り抜きは公式と同じ土俵で戦うことになる。差別化（第4章）が成立しなければ埋もれる。

## 3. 許諾 — 2つの関門

性質が異なる2つを、それぞれ通す必要がある。

### 関門① 権利者側（ガジェット通信MCN）

- 申請フォーム: <https://forms.gle/knE8kFVfjTgr7Qa89>（令和の虎Second）
- **大島さん自身が送信する。** 契約意思の表明であり、氏名・チャンネル情報・分配率の合意を含むため代理送信はしない
- フロー: 申請 → チャンネル運営 → YouTube収益化審査クリア → MCN紐付け → 分配率に応じて毎月ガジェット通信経由で権利者へ支払い
- **収益は全額残らない。** 分配率は申請時に権利者と合意する

既存の令和の虎Youth切り抜きch（`@reitoraacademy2`、9.21万人）の概要欄にも
「本チャンネルはガジェット通信社に申請済みです。」と明記されており、この経路が実運用されている。

### 関門② YouTube側

- YPP参加条件（登録者1,000人＋公開動画の総再生4,000時間、または Shorts 1,000万回）
- **再利用コンテンツ審査**。2024年10月と2025年7月に厳格化され、
  「字幕を付けただけ」「BGMを変えただけ」は独自の付加価値と認められない
- 関門①を通っても②は別途通す必要がある

**公開は関門①が通ってから。** 実装と1本目のビルドまでは先行してよい。

## 4. 付加価値の型 — 図解カード

既存競合の売り文句は「字幕付きで音が出ない状況でも見られる」で統一されており、
**全員が字幕止まり**。図解は空いている。

令和の虎は「志願者が事業計画を持ち込む → 虎が詰める → 出資判定」という定型構造を持つ。
この構造に、元動画には存在しない整理を重ねる。

| カード | 差し込み位置 | 内容 |
| --- | --- | --- |
| 案件カード | 冒頭 | 希望金額 / 事業内容 / 志願者の経歴 |
| 論点カード | 詰めどころ | 虎の指摘を1行に圧縮 |
| 判定カード | 末尾 | 誰がいくら出したか。決裂ならその理由 |

構造が定型なのでテンプレ化でき、自動生成と相性が良い。
収益化審査でも「元の配信に無い独自の付加価値」として具体的に主張できる。

**ナレーションは入れない**（声出しなし）。付加価値はテロップと図解のみで作る。

## 6. アーキテクチャ

新規リポジトリ `projects/tora-kirinuki`。`bgm-youtube` とは独立させる。
投稿先チャンネルもGoogleアカウントも別であり、片方の事故がもう片方を壊さない
（`bgm-youtube` が `BGM-create` に対して一方向依存を保っている設計判断と同じ）。

`upload_youtube.py` は参照ではなく **`bgm-youtube` からコピーして持つ**。
GCPプロジェクト `bgm-youtube-504706` は流用可（YouTube Data API v3 有効化済み）。
`token.json` はチャンネルが違うので別管理。

```
Phase 0  申請（大島さん）── ガジェット通信フォーム
   ↓
1. fetch_source.py    本編DL + 日本語字幕 + メタ    → work/<video_id>/
2. probe_signals.py   Most replayed + コメント言及  → work/<video_id>/signals.json
3. find_moments.py    3点合成スコアで候補区間抽出   → work/<video_id>/candidates.json
   ↓ レシピ作成（原稿はLLM生成、大島さんが最終確認）→ recipes/<id>.json
4. build_clip.py      カット + テロップ + 図解カード → work/<id>/video.mp4
5. upload_youtube.py  private → 内容確認 → --publish → state/published.json
```

ディレクトリ構成も `bgm-youtube` に揃える。

```
tora-kirinuki/
  scripts/       パイプラインの各段
  recipes/       <id>.json（1本 = 1レシピ）
  work/          ビルド中間物（Git管理外）
  state/         published.json（公開実績）
  docs/          設計・運用手順
```

## 7. コンポーネント仕様

### 7.1 `fetch_source.py`

`@reiwanotora_second` の新着を yt-dlp で取得する。

- 入力: `--latest N` / `--since YYYY-MM-DD` / 個別URL
- 出力: `work/<video_id>/` に `source.mp4`、`subs.json`（[(秒, 行), ...]）、`meta.json`
- `libecity-library/scripts/fetch-youtube.py` に**動作実績のあるVTTパーサとチャンネル抽出**があるので移植する
  - `extractor_args = {"youtube": {"lang": ["ja"]}}` を必ず付ける。付けないとタイトル・チャプター名が自動翻訳で英語になる
  - チャンネル一覧はRSS（`feeds/videos.xml`）ではなく yt-dlp のチャンネル抽出を使う。RSSは500/404を返すことがある
  - 自動字幕のVTTは2行ローリング表示で同じ文字列が繰り返される。重複除去が要る
- 取得済みは再取得しない（`--force` で上書き）

### 7.2 `probe_signals.py`

「いい場面のリサーチ」の中核。**Most replayed ヒートマップは YouTube Data API では取得できない**ため、
ブラウザ経由で取る。

- Most replayed: 本編ページの `ytInitialData` / player response に含まれるヒートマップ配列
- コメントのタイムスタンプ言及: `12:34` 形式の言及を本文から抽出し、秒に正規化して集計
- 出力: `work/<video_id>/signals.json`

```json
{
  "video_id": "...",
  "heatmap": [{"start": 0, "end": 30, "score": 0.42}],
  "comment_marks": [{"seconds": 754, "count": 12, "samples": ["12:34 ここ好き"]}]
}
```

コメントは YouTube Data API の `commentThreads.list`（1リクエスト1ユニット）でも取れる。
ヒートマップだけがブラウザ必須。

### 7.3 `find_moments.py`

3信号の合成でスコアリングする。

| 信号 | 何を表すか |
| --- | --- |
| Most replayed の山 | 視聴者が繰り返し戻る場所 |
| コメントのタイムスタンプ言及 | 視聴者が語りたくなる場所 |
| 字幕 | そこで何が起きているか |

**3つが重なる区間が最良の切り抜き地点**。
上位N区間を `candidates.json` に出す。各候補は開始・終了秒、スコア内訳、該当字幕を持つ。

区間は発話の切れ目にスナップする（字幕のキュー境界を使う）。文の途中で切らない。

### 7.4 レシピ

`recipes/<id>.json`。原稿はLLMが生成し、大島さんが最終確認する。

```json
{
  "id": "2026-08-10-example",
  "source_video_id": "xxxxxxxxxxx",
  "source_url": "https://www.youtube.com/watch?v=xxxxxxxxxxx",
  "source_title": "【FULL】「...」（元動画のタイトル）",
  "clip": { "start": 742.0, "end": 1180.5 },
  "cards": {
    "brief": { "amount": "希望金額 500万円", "business": "事業内容", "profile": "志願者の経歴" },
    "points": [{ "at": 830.0, "text": "虎の指摘を1行に圧縮" }],
    "verdict": { "result": "成立", "detail": "誰がいくら出したか。決裂ならその理由" }
  },
  "title": "動画タイトル",
  "description": "本文（元動画URL・タイトルは自動で冒頭に挿入される）",
  "tags": ["令和の虎", "切り抜き"],
  "expected_channel_id": "UC...",
  "privacy_status": "private"
}
```

### 7.5 `build_clip.py`

- ffmpeg で `clip.start` 〜 `clip.end` を切り出す
- 図解カードは Pillow で PNG を生成して合成する。`bgm-youtube/scripts/build_banner.py` と同じ手法
- 字幕は `subs.json` から該当区間を焼き込む
- 出力: `work/<id>/` に `video.mp4` / `thumb.png` / `description.txt` / `meta.json`
- `--dry-run` で候補と尺の試算のみ

### 7.6 `upload_youtube.py`

`bgm-youtube` からコピーして流用する。private で投稿 → 内容確認 → `--publish`。

## 8. 許諾条件をコードで担保する

規約違反は事故ではなく**バグとして防ぐ**。運用の注意書きに頼らない。

| 条件 | 実装 |
| --- | --- |
| 概要欄の冒頭に元動画URL・タイトル | `description.txt` 生成時にレシピの `source_url` / `source_title` から**自動挿入**。手書きさせない |
| 投稿先チャンネルの誤り防止 | `expected_channel_id` を必須項目にし、不一致なら中断。過去に別チャンネルへ誤投稿した事故があるため |
| 誹謗中傷・過度な煽り | タイトル生成時にNGワードでガード |
| Inauthentic content ポリシー | タイトル・概要欄・タグをテンプレの使い回しにしない |

## 9. エラー処理

`bgm-youtube` で踏んだ罠を踏襲する。

- **素材の実在は開始前に全部確認する。** ffmpeg が途中で落ちるより、何が無いかを先に出したほうが直しやすい
- **尺は `-t` で明示し、ビルド後に差分を検証する。** 1秒を超える差があれば失敗させる
- yt-dlp の取得失敗・日本語字幕の欠落は警告ではなく明示的に失敗させる
- `thumbnails.set` はチャンネルの電話番号確認が無いと403になる。失敗しても停止せず警告して続行し、`published.json` に記録する

### 字幕はASRであることの帰結

自動字幕は音声認識なので**固有名詞と数値が崩れる**。
令和の虎は**金額が命**であり、カードに載せる数字を字幕から取ると誤情報を流すことになる。

**カードに載せる金額・社名・人名は字幕を信用せず、映像で裏取りする手順をレシピ作成に組み込む。**
`build_clip.py` は `cards.brief.amount` が空のままならビルドを失敗させる。

## 10. テスト

- **1本を通しで公開まで検証する**（`bgm-youtube` の立ち上げと同じやり方）
- 図解カードは PNG 単体で先に目視確認する
- `--dry-run` で候補区間と尺を試算してから本ビルド
- `find_moments.py` は既存の人気切り抜きが扱った区間を正解データにして、スコア上位に入るか確認する

### 「日本の最新ニュースまるわかり」を採らなかった理由

登録者2,840人でYPPの登録者要件は満たすが、**166本すべてがShortsで長尺が1本も無い**。
YPPのもう一方の条件（長尺の総再生4,000時間、またはShorts直近90日1,000万回）に対し、
長尺の視聴時間はほぼゼロ、Shorts累計も1,259,943回で1,000万回には遠い。
**収益化要件は満たしていない。**

加えて既存動画を非公開にすると、YPPの集計対象は公開動画のみなので
Shortsの126万回も消え、引き継げるのは登録者数だけになる。
その2,840人は政治ニュース目当ての層で、令和の虎の切り抜きには反応しにくく、
初動の視聴維持率とクリック率を下げてアルゴリズム上むしろ不利になりうる。
