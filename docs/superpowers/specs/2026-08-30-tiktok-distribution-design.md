# TikTok への配信 — 設計

作成: 2026-08-30

## 1. 何をするか

**いま作っている縦型ショートを、YouTube Shorts と TikTok の両方に出せるようにする。**

新しい動画の種類は作らない。**尺の方針を1本に決め直し**、TikTok へ手で投稿するための
テキストを添えて出すだけ。1つのビルドが2つのプラットフォームに乗る。

## 2. なぜこの形にしたか

当初は「TikTok用に1分超の別バリアントを作る」設計だった。実測を数えてやめた。

### TikTok の収益化条件

| 項目 | 条件 |
| --- | --- |
| 動画の尺 | **1分以上**（15秒・30秒などの短尺は対象外） |
| フォロワー | 1万人以上 |
| 再生 | 直近30日で10万回以上（累計ではない） |

出典: [TikTok Newsroom](https://newsroom.tiktok.com/ja-jp/tiktok-creator-rewards-program) /
[クリエイターアカデミー](https://www.tiktok.com/creator-academy/article/creator-rewards-program/?lang=ja)

### このチャンネルが既に持っている実測

`scripts/recipe.py` の `SHORT_RECOMMENDED_SEC` のコメント（2026-08-13 実測）:

> 令和の虎塾のショートは **67〜73秒**で公開1〜4日に **3,925〜28,477再生**。
> 【忙しい人のための】は22〜37秒。こちらの **103秒・132秒は0〜2再生**だった。

### 既存25本のレシピ上の尺

```
中央値 63.0s / 最短 43.0s / 最長 138.0s
  65〜66秒 ── 9本（最多帯）
  60〜63秒 ── 7本
  43〜57秒 ── 7本
  102・138秒 ── 2本（0〜2再生だったもの）
```

**TikTok の収益化ライン（1分以上）と、実測の高再生ゾーン（67〜73秒）が重なる。**
別々の版を作る理由が無いので、バリアント機構を捨てて尺の方針だけを直す。

## 3. 変更点

### 3.1 `short` の尺に下限を入れる（`scripts/recipe.py`）

| | 現在 | 変更後 | 根拠 |
| --- | --- | --- | --- |
| 下限 | なし | **65秒未満はエラー** | TikTok は1分以上。ffmpeg の実測誤差 ±1秒（`DUR_TOLERANCE`）と TikTok 側の処理で数フレーム削られる分の余裕を取る |
| 推奨上限 | 75秒で警告 | **73秒**で警告 | 実測の高再生ゾーンの上端 |
| ハード上限 | 180秒でエラー | 180秒（据え置き） | YouTube Shorts の仕様 |

**狙う窓は 65〜73秒。**

判定は `validate_short` の既存の流れに乗せる。**巻き戻し後の長さで測る**
（`rewind_to_topic_head` は開始点を手前に動かすので、レシピの値より長くなることはあっても
短くなることはない）。

新しい定数を1つ足す:

```python
SHORT_MIN_SEC = 65.0   # TikTok の収益化対象は1分以上。実測誤差の余裕を含めた下限
SHORT_RECOMMENDED_SEC = 73.0   # 75.0 から引き下げ
```

### 3.2 `caption.txt` を出す（`scripts/build_short.py` / `scripts/recipe.py`）

TikTok は手で投稿するので、貼り付けるテキストをビルド時に出す。
`work/<id>-short/caption.txt` に置く。

構成:

1. フック（`short.hook`、または `short.title` があればそれ）
2. **元動画のタイトルとURL** — ガイドライン必須の「概要欄に元動画へのリンク」
3. `scripts/recipe.py` の `CREDIT`（「申請済み」の事実のみ。「公式」「公認」は書かない）
4. ハッシュタグ（`recipe.tags` から生成）

**URL は TikTok のキャプションではリンクにならないが、必須条件を満たす意図として書く。**
あわせて TikTok のプロフィールに YouTube チャンネルへのリンクを置く（手作業・1回だけ）。

`build_description()` は YouTube 用の長文なのでそのまま使わない。
`build_caption()` を新設し、`build_description()` と同じ材料から短い版を組む。
元動画URLの挿入は両方で共通の関数に寄せ、**手書きさせない**という既存の担保を崩さない。

### 3.3 `state/tiktok.json` で別台帳（新規）

**`state/published.json` には絶対に書かない。** これは `upload_youtube.py` が
`__file__` 基準で管理する YouTube 専用の台帳で、TikTok を混ぜると壊れる。

`state/tiktok.json` の形:

```json
{
  "videos": {
    "2026-08-29-mai-namesugi-short": {
      "recipe_id": "2026-08-29-mai-namesugi",
      "posted_at": "2026-09-04",
      "url": "https://www.tiktok.com/@.../video/...",
      "duration_sec": 70.1
    }
  }
}
```

**手で書く。** 投稿が手作業なので、記録も手作業でよい。スクリプトは書かない。

**YouTube Data API のクォータを1ユニットも使わない。** 1日10,000の制約と完全に独立するので、
既存の公開ペース（1日 長尺1本・ショート2本）に影響しない。

## 4. 投稿を自動化しない理由

TikTok Content Posting API は、**審査を通していないクライアントは `SELF_ONLY`
（自分だけ閲覧）でしか投稿できない。** 公開投稿には `video.publish` スコープの審査が必要で、
2〜4週間かかり、複数回のフィードバック往復がある。審査では「投稿前にクリエイターの
ユーザー名とアバターを表示すること」などが必須要件になる。

出典: [Get Started - Direct Post](https://developers.tiktok.com/docs/en/content-posting-api-get-started) /
[TikTok Content Posting API in 2026](https://www.postpeer.dev/blog/best-tiktok-posting-api)

**1日2本の手作業に、2〜4週間の審査とアプリ実装を先に払う価値は無い。**
投稿本数が増えて手作業が痛くなってから考える。

## 5. 許諾 — 投稿の前に照会する

**権利者の立場は「あくまで黙認」**（`README.md`）。許諾は**チャンネルID単位**で、
実際に旧チャンネルの許諾は引き継がれず新チャンネルで取り直している
（`docs/daily-workflow.md`）。

[ガイドライン](https://reiwanotora.jp/clipping-guidelines/) 12項を全文確認した結果、
**投稿先プラットフォームについての記載は無い。** ただし「書いていない＝許されている」とは
読めない材料が揃っている:

- 6項が「**YouTube**パートナープログラム収益化の有無問わず事前申請が必要」と YouTube 前提
- 4項・5項が「**チャネル名**」の規定で、YouTube チャンネルを想定した書き方
- 11項「派生チャネル動画の切り抜きは**各チャネルの登録フォームで申請**」＝範囲が変われば申請し直す建て付け
- 収益の経路が MCN 紐付け → ガジェット通信経由で権利者へ支払い。TikTok にはこの配管が無い
- **警告1ヶ月3回で申請取り消しの可能性**

つまり下振れが「TikTok がダメだった」ではなく「**YouTube 側の許諾ごと失う**」になり得る。

### 決めたこと

**mp4 を作ることにリスクは無い。リスクは「投稿」にだけある。**

```
ステップ0  get-clip@razil.jp へ照会（大島さんが送信）
           ※ 契約意思の表明なので代理送信しない（2026-08-09 設計書の方針を踏襲）
   ↓ 返事を待つ間も制作は止めない
ビルド     work/<id>-short/ に video.mp4 と caption.txt を貯める
   ↓ 返事が来てから
投稿       TikTok へ手で投稿し、state/tiktok.json に記録
```

照会文の草案はこの仕様書の実装時に用意する。

## 6. 副作用

### 6.1 既存14本は65秒未満なのでビルドし直せなくなる

14本の内訳は公開済み13本＋未公開1本（`mai-namesugi`。6.2 で切り直す）。

**これは正しい挙動として受け入れる。** 作り直しても収益化対象外の資産にしかならず、
公開済みショートの差し替えは取り下げ扱いになる（`HANDOFF.md`）。
`--thumb-only` 相当の操作は `build_short.py` に無いので、実運用で困る場面は無い。

### 6.2 `2026-08-29-mai-namesugi-short` は切り直す

43.0秒で下限割れ。**まだ未公開**なので上げる前に直せる。

| | 現在 | 変更後 |
| --- | --- | --- |
| `short.start` | 1516.399 | **1489.279** |
| `short.end` | 1559.399 | 1559.399（据え置き） |
| 尺 | 43.0s | **70.1s** |

`rewind_to_topic_head(1489.279)` は **1489.279 [文頭]** に着地する（巻き戻し無し・確認済み）。
中身は「TikTokも事業も人にものが売れる時代」→「このプラン内容でも売れると思ってるんすか」
→「これが半年間の最高傑作」→「舐めすぎでしょ」→「そこに行ってもあなたはいない」。

**この切り直しは尺の下限を実装する前に、通常の運用として先に行う**（本日 16:00 の
アップロードに間に合わせるため）。

## 7. テスト

| # | 内容 | 落ちるべき条件 |
| --- | --- | --- |
| 1 | **既存の出力が変わらない** | 65〜73秒に収まる既存レシピ1本をビルドし、尺・字幕枚数・`meta.json` が変更前と一致しない |
| 2 | 65秒未満でエラー | 64.9秒のレシピが通ってしまう |
| 3 | 巻き戻し後の長さで測る | レシピ上62秒でも巻き戻しで66秒になるものがエラーになる |
| 4 | 73秒超で警告（エラーではない） | 74秒がエラーになる、または警告が出ない |
| 5 | 180秒超はエラーのまま | 既存の上限判定が壊れる |
| 6 | `caption.txt` に元動画URLが入る | URLが欠ける |
| 7 | `caption.txt` に `CREDIT` がそのまま入る | `CREDIT` が欠ける・改変される |
| 8 | `with_short()` の既定（50秒）を直しても、字幕・巻き戻し・上限のテストが通る | 下限の追加で既存3本が巻き添えで落ちたまま |

**テスト7は「公式」の単純禁止では書けない。** `CREDIT` 自体が
「公式チャンネルではありません」という否定文なので、`CREDIT` がそのまま
入っていることを見る。

**下限の追加で既存テスト3本が落ちる**（`with_short()` の既定が50秒のため）。
`test_正しいショートは通る` / `test_字幕があれば通る` / `test_開始が発話の途中なら警告する`。
フィクスチャの尺を窓の中に直す。

テスト1が最重要。**公開済み44本と既存11レシピが依存している挙動を変えない**ことを固定する。

## 8. やらないこと

- TikTok Content Posting API の実装と審査申請（4章）
- `state/tiktok.json` を書くスクリプト（手作業で足りる）
- 公開済みショートの差し替え（取り下げ扱いになる）
- TikTok 専用の別区間・別カット（2章の実測により不要）
- 長尺（15分）の TikTok 転載（縦型でなく、図解カードの読みも合わない）
